# 参加登録ボタンの挙動仕様

本ドキュメントでは、イベントおよび日程調整における参加登録ボタンの表示条件と挙動を定義します。

## 参加ステータスと遷移

`EventParticipant.status` の取りうる値と意味。

| 値 | 意味 | 一覧での扱い |
|---|---|---|
| `attending` | 参加 | 表に出す。定員の消費対象 |
| `maybe` | 未定 | 折りたたみの中 |
| `participation_request` | 参加リクエスト（承認待ち） | 折りたたみの中 |
| `not_attending` | 欠席 | 折りたたみの中 |
| `cancelled` | 回答の取り消し | 折りたたみの中 |

### 遷移

骨子は **「一度出した回答は、取り下げるならキャンセル」**。

| 現在 ＼ 変更先 | 参加 | 未定 | リクエスト | 欠席 | キャンセル |
|---|---|---|---|---|---|
| 参加 | －(内容変更) | ❌ | ❌ | ❌ | ✅ |
| 未定 | ✅ | －(内容変更) | ❌ | ❌ | ✅ |
| 参加リクエスト | ❌ | ❌ | －(内容変更) | ❌ | ✅ |
| 欠席 | ✅ | ✅ | ❌ | －(内容変更) | ✅ |
| キャンセル | ✅ | ✅ | ✅ | ❌ | －(内容変更) |
| （記録なし） | ✅ | ✅ | ✅ | ✅ | － |

- **参加からはキャンセルだけ。** 未定や欠席へは下げられない
- **参加リクエストからもキャンセルだけ。** 参加への昇格は主催者の承認であって、
  利用者が自分で行う操作ではない
- **欠席には戻れない。** 「参加すると言ったが欠席」と「最初から欠席」を
  同じ状態にすると、主催者から見て人数の動きが追えなくなる
  （`cancellationReason` も残らない）
- 同じ状態への変更（コメントやオプションの手直し）は常に可能

実装は `src/lib/status-transition.ts` の `ALLOWED_USER_TRANSITIONS`。
判定は `canUserChangeStatus`、画面の選択肢は `allowedUserTargets` から作る。
呼び出し元は `PUT /api/v1/events/[id]/participate` と `ParticipateDialog`。

**画面とサーバーで規則を書き分けないこと。** 片方だけ変えると、
画面からは選べるのにサーバーが弾く状態になる。

### 主催者・幹事の操作（参加者を編集）

主催者・幹事は**状態を選ばない。状態ごとに決まった操作を押す。**
押すと確認のモーダルを出し、**その場で反映する**（まとめて保存しない）。

| 現在 | 操作 | 結果 |
|---|---|---|
| 参加リクエスト | 承認 / 拒否 | 参加 / キャンセル |
| 参加・未定 | キャンセルにする | キャンセル（**幹事も外れる**） |
| 参加・未定 | 幹事にする / 幹事を解除 | 幹事の有無だけ変わる。**作成者だけ**ができ、作成者自身は対象外 |
| 欠席・キャンセル | 削除 | **記録ごと消す**（選んだオプション・出欠の記録も） |

- **参加へ引き上げられるのは承認だけ。** 規約への同意を取っているのは
  本人が参加・未定・参加リクエストを選んだときだけで、欠席やキャンセルから
  引き上げると同意していない参加者ができる。未定は本人が「まだ決められない」と
  言っている状態で、主催者が代わりに確定させるものではない
- **欠席・キャンセルは削除しかできない。** 状態を動かさず、回答したこと自体を
  無かったことにする。消えた人は `viewer.participation` が `null` に戻り、
  一から参加登録できる
- **キャンセルにしたら幹事を外す。** 幹事の権限（`checkOrganizerPermission`）は
  参加状態を見ないので、残すと参加していない人が参加者を編集できる
- 定員を超えて承認したら、定員のほうを増やす
- 読んでから書くまでに状態が変わっていたら書かない（409）。本人が同時に
  キャンセルした人を承認すると、同意の無い参加者ができる

実装は `src/lib/status-transition.ts` の `allowedAdminActions`。画面のボタン
（`EditParticipantsScreen`）とサーバーの判定
（`PATCH` / `DELETE /api/v1/events/[id]/participants/[userId]`）がどちらもここから作る。

### 記録の有無と HTTP メソッド

**「表示上未参加」と「記録がない」は別。** 一度キャンセルしても
`eventParticipant` の行は残るため、再登録は POST（作成）ではなく
PUT（更新）になる。画面は `viewer.participation` が `null` かどうかで
判断する（`status` では判断しない）。

### 締切との関係

**締切後は利用者側から状態を動かせない**（`participation_request` を除く）。
締切を過ぎた `maybe` は auto-cancel-maybe が自動で `cancelled` に変える
（`src/server/services/auto-cancel-maybe.ts`）。手で変えられるようにすると
自動処理と食い違って人数が揺れる。締切後に事情が変わった場合は主催者へ
連絡してもらう。

**参加リクエストは締切の対象外。** `allowParticipationRequest` が有効なら、
満員のときだけでなく締切後も申し込める（主催者が承認して参加に変える）。
画面もこれに合わせて、締切後は「参加をリクエスト」を出す。

自動キャンセルの実行経路:

| 経路 | いつ |
|---|---|
| `GET /api/v1/events/[id]`（`after()`） | 詳細を開いたとき。表示のための保険 |
| `POST /api/v1/cron/maintenance` | 2時間おきの定期的な後片付け（`server/services/maintenance.ts`）。誰も詳細を開かないイベントも片付く |
| `POST /api/v1/events/auto-cancel-maybe` | 管理者が手で一括実行 |
| `POST /api/v1/events/[id]/auto-cancel-maybe` | 個別に手動実行 |

いずれも `updateMany` で冪等。同時に走っても、実行されなくても壊れない。

### 規約同意

参加規約は `attending` / `maybe` / `participation_request` にだけ求める。
欠席する人に参加規約への同意を求めるのは筋が通らないし、同意しないと
欠席の回答すら残せなくなる。

## 操作の出し分け

**状態は純関数が導く。** 画面は導かれた `kind` を描くだけで、条件を
組み立て直さない。分岐が多く、順序を間違えると「中止されたイベントに
参加できる」といった事故になるため、画面から切り離してテストしてある。

| | イベント | 日程調整 |
|---|---|---|
| 判定 | `components/event/resolveActionState.ts` | `components/pre-event/resolvePreEventActionState.ts` |
| 描画 | `components/event/EventAction.tsx` | `components/pre-event/PreEventAction.tsx` |

### イベント（`EventActionState`）

判定の順序には意味がある。

1. **幹事** (`host`) … 主催者は中止後も参加者への連絡などで管理を続ける
2. **イベントの状態** (`cancelled` / `ended`) … 参加以前の問題
3. **回答済み** (`registered`) … 締切後も自分の状態は見える必要がある。
   **欠席も回答として扱う**（「参加していない」と「まだ答えていない」を
   同じ姿にすると、欠席と答えた人に再び参加登録を促すことになり、
   答えを変える入口も消える）。`cancelled` だけは未回答に戻す
4. **未ログイン** (`anonymous`)
5. **資格** (`ineligible`) … プラットフォームやサーバーの条件を満たさない。
   **`closed` と混ぜない。** 締切は待てば分かるが、こちらは何をしても参加できない
6. **締切** … `requestable`（リクエスト可）か `closed`
7. **定員** … `requestable` か `full`
8. それ以外は `open`

### 日程調整（`PreEventActionState`）

同じ考え方だが**状態は少ない** — 定員も参加リクエストも無いため。
`host` / `ended` / `anonymous` / `ineligible` / `closed` / `answered` / `open` の7つで、
終了の判定は**未来の候補日が1つも無いこと**（日程調整に開催日は無いので、
一覧の絞り込みと同じ規則で候補日から決める）。

`host` `closed` `ended` は `answered` を併せ持つ。終了後・締切後でも
「自分が答えたこと」は見えなければならない。

### 文言と見た目

ボタンの文言は `EventAction.tsx` / `PreEventAction.tsx` に置く。色で状態を
足さない — ボタンは primary / default / destructive の3種だけで、
用途ごとに色を増やさない（`docs/DESIGN_GUIDELINES.md`）。

組み合わせの表はここに持たない。`resolveActionState.test.ts`（22件）と
`resolvePreEventActionState.test.ts`（10件）が固定している。**表を文書に
書き写すと、片方だけ直した日に嘘が残る。**
