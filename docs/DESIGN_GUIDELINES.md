# デザインガイドライン

全画面に適用する。個別画面の詳細設計はこの文書の制約の中で決める。

---

## 1. コンセプト

**ニューモーフィズム**と **Liquid Glass** を併用する。ただし両者は本来相反する
（前者は不透明な面からの押し出し、後者は透過とぼかしの重なり）ため、
**適用面を分ける**。混在させると濁る。

| 手法 | 適用面 | 具体例 |
|---|---|---|
| **ニューモーフィズム** | 不透明な面の上に置く**操作可能な要素** | ボタン、トグル、セグメント、入力欄のフォーカス面 |
| **Liquid Glass** | 背景の上に**浮いている層** | ヘッダー、モーダル、ドロップダウン、モバイルのアクションバー |
| **フラット** | 情報を読ませる面 | カード本体、テーブル、本文 |

**カードには立体表現を使わない。** カードまで押し出すと画面全体が凹凸になり、
どれが押せるのか分からなくなる。カードは境界線と控えめな影のみ。

### 守るべき制約

ニューモーフィズムは影で立体を作るため**背景と前景の明度差が小さくなりやすい**。
とくにダークモードで読みにくくなる。以下は立体表現より優先する。

- 本文テキストと背景のコントラスト比 **4.5:1 以上**
- ボタンのラベルと面のコントラスト比 **4.5:1 以上**
- **押せる要素は影だけで示さない。** 影に加えて、境界・ラベル・カーソル形状の
  いずれかで判別できること（影はダーク背景や高コントラストモードで消える）
- フォーカスリングは立体表現に埋もれさせない。`--ring` を明示的に描く

---

## 2. 配色

**青系を基調とする。** primary は青。

- ライト/ダーク両対応。すべての色はセマンティックトークン経由で指定し、
  コンポーネントに16進やユーティリティの色名を直書きしない
- 既定テーマは**OS の設定に従う**（`system`）

---

## 3. 角丸

| 対象 | 値 |
|---|---|
| 既定（ボタン、入力欄、バッジ、メニュー項目） | `rounded-lg` |
| カード、モーダル、パネル | `rounded-xl` |

これ以外の角丸は使わない。丸ボタンやアバターなど円形が必然のものは `rounded-full`。

## 4. ボタン

**既定の大きさは h-12（48px）。** 小さくするのは「行の中に置く補助的な操作」
だけに限る（`sm` = h-9、`xs` = h-8）。h-8 は指の的として小さすぎる。
アイコンだけのボタンは同名のサイズと高さを揃える
（`icon` = size-12、`icon-sm` = size-9）。

**例外はイベント・日程調整の詳細画面の操作列**（§7）。情報行の
「カレンダーに追加」に合わせて `sm` でそろえている。h-12 のままだと
同じ画面に2つの高さが並び、揃っていないことのほうが目に付いた。
**本文の頭に単独で置く参加ボタンだけは h-12 のまま。** あそこは画面で
最初に目に入る操作で、周りに高さを合わせる相手がいない。


**色は primary とそれ以外の2系統のみ。** 「それ以外」は中立色（グレー系）で、
用途ごとに色を増やさない。

| 種別 | 用途 |
|---|---|
| `primary` | その画面で最も進めたい操作。1画面に原則1つ |
| `default` | それ以外すべて（キャンセル、閉じる、副次的な操作） |
| `destructive` | 削除・BAN など取り消せない操作。**確認ダイアログと必ず併用** |

- 将来 CTA 専用色を追加する可能性があるが、**現時点では導入しない**
- すべてのボタンは立体感を持つ（押し込みの状態変化を含む）

### 装飾用の色（ボタン色ではない）

| トークン | 用途 |
|---|---|
| `--calendar-accent` | 日付バッジの赤。日付であることを一目で示すための装飾 |
| `--calendar-paper` | 日付バッジの紙面。**ダークでも白地・黒文字で固定する**（テーマに追従させるとカレンダーに見えない） |

**操作可能な要素には使わない。** 押せる要素の色を増やさないという原則は、
装飾には及ばない。逆に、装飾用の色をボタンに流用してはならない。

### 状態を兼ねるボタン（`state`）

**色相は増やさない。primary と同じ青のトーナル（淡い面）で表す。**

| トークン | 用途 |
|---|---|
| `--primary-surface` | 面。**カードとのコントラストを 1.2 以上持たせる** |
| `--primary-surface-hover` | ホバー時の面。明度を 0.03 以上動かす |
| `--primary-surface-foreground` | 文字・アイコン。面の上で 4.5:1 以上 |

境界は `border-primary/70`。塗りの強さで primary と区別する。

| | 塗り | 意味 |
|---|---|---|
| `primary` | 青の塗りつぶし | 押してほしい。まだ終わっていない |
| `state` | 青の淡い面＋濃い青の文字＋青の境界 | 確定している。押す必要はないが操作はできる |

使ってよい例:
- 参加登録済み・未定で回答済み（自分の状態）
- 幹事メニュー（自分が主催しているという状態への入口）

**新しい操作の色として増やしてはならない。**

理由: 操作の色を primary とそれ以外の2系統に絞った結果、
「登録済み」と「押せない」と「副次操作」がすべて中立色になり見分けが
つかなくなった。**足りないのは操作の色ではなく状態の強弱**だった。

#### 面のコントラストも測る

- **緑（`--success`）にしない。** 画面で最も目立つボタンだけ色相が違うと、
  他の青と系統がつながらない
- **文字だけでなく面もカードと比べる。** 淡すぎる面は白いカードに溶けて
  ボタンに見えない。文字のコントラストが足りていても、**文字だけ見ていると気づけない**

面を独立したトークンにしているのは、淡い塗りだけだと立体表現が
背景に溶けて「押せる」ことが伝わらなくなるため。とくにダークでは
**面を背景より明るく**する必要がある（暗いままだと影が沈んでボタンに見えない）。
`src/app/globals.contrast.test.ts` が文字と面の両方を数値で押さえている。

**淡い青の面は `Notice` の `primary/10` と紛らわしい。** 知らせの面は
状態ボタンより明らかに薄くし、立体表現を付けない。同じ濃さにすると
「読むだけの知らせ」が押せるものに見える。

### 情報の強弱（バッジ・タグ）

文字色だけの違いでは差が伝わらない。3段階で描き分ける。

| 種類 | 見た目 | 意味 |
|---|---|---|
| タグ（ハッシュタグ等。`Tag`） | 塗り（中立色）・境界なし | 分類。読み飛ばしてよい |
| 参加条件（`ConditionLink`） | 塗り（中立色）・境界なし | 必要なら読む |
| 参加条件の強調（`ConditionLink` の warning） | 淡い青の塗り＋青文字＋太字 | 締切・残席など読んでほしい |

**青は強調のために空けておく。** タグを青にすると、重要な情報と
同じ色が並んで強弱が消える。

#### 参加条件はボタンの姿をさせない

題名の下の参加条件（締切・定員・参加できるアカウント・参加規約）は、
**平らな文字**にする。境界も影も持たせない。

すぐ上に「参加登録」があるので、その下にボタンの姿をした面を横一列に並べると、
**読ませたい条件が操作の列に見える**。立体で「押せる」を示す必要はない — 末尾の `＞`
が合図になる。

| 押した先 | |
|---|---|
| **一律でモーダル** | 締切・定員・参加できるアカウント・参加規約 |

ポップオーバーと混ぜない。開くまでどちらか分からないものを隣り合わせに
置くと、開いた瞬間に画面のどこを見ればよいかが毎回変わる。

### 罫線

**区切りは必ず1pxの線で引く。** 影は彫りを足す飾りで、強制カラーや
高コントラストで消えても区切りは失われない。

| クラス | 引く場所 |
|---|---|
| `.rule-y` | 節の**上下の縁と、子どうしの間** |
| `.rule-t` | 上の縁だけ |

- **間だけに引かない。** 上下を開けたままにすると、並びがどこから始まって
  どこで終わるのかが最初と最後の行だけ本文の余白に溶ける
- **中身が無いときは節ごと出さない。** 空の節に上下の線だけが残ると、
  何も無い隙間を2本の線が囲うことになる
- 彫り（線の下1pxのハイライト）が効くのは**ダークだけ**。ライトの地は
  純白（`--background: oklch(1 0 0)`）で、白より明るい色は作れない。
  ライトでは線そのものを `--border` より一段濃くして輪郭を出している。
  ここで無理に立体を出そうとすると、地を灰色に濁らせることになる

## 5. フォーム部品

**任意の入力欄は「＋◯◯を指定」で足す。** トグルで出し入れしない。
ここで決めているのは設定のオン・オフではなく「入力欄を出すかどうか」で、
状態を持つスイッチより、その場の操作のほうが素直に読める。
足した欄は「✕」で取り消せる（値も一緒に消す）。


**チェックボックスとラジオは使わない。**

| 入力 | 部品 |
|---|---|
| 単一の真偽値 | `ToggleSwitch` / `ToggleField`（スライドトグル） |
| 規約への同意 | `ConsentCheckbox`（**唯一の例外**） |
| グループから1つ選ぶ | `OptionGroupField`（`multipleChoice: false`） |
| グループから複数選ぶ | `OptionGroupField`（`multipleChoice: true`） |

- **同意だけはチェックボックスにする。** トグルは「設定のオン・オフ」に
  読めるが、同意は切り替える設定ではなく、読んだうえで印を付ける行為。
  ネイティブではなく Radix の `Checkbox` を包んだ `ConsentCheckbox` を使う
- **すべてコンポーネント化する。** 画面側で `<input type="checkbox">` や
  `<input type="radio">` を直接書かない
- 選択部品の影は**ボタンより弱くする**（`.raised-subtle`）。選択肢が横に
  何個も並ぶため、ボタンと同じ強さだと画面が凹凸だらけになる
- **選択済みを色だけで示さない。** チェックマークや点を併用する
  （色覚特性によっては差が分からない）

イベントのオプションは `EventOptionGroup` / `EventOption` の2階層で、
グループごとに単一／複数選択が切り替わり、選択肢に定員が付くことがある。
満席の選択肢は選べないが、**既に選んでいる場合は解除できる**ようにする。

理由: ネイティブのチェックボックスは `color-scheme` に強く影響され、
ブラウザ・OS 設定によって見た目が破綻する（未チェックが真っ黒になる、など）。描画を自前で持つことで環境差をなくす。

## 6. レイアウト

- 全ページが**ヘッダーとフッターを持つ**。`layout.tsx` で一度だけ描画し、
  各画面から import しない
- **トップページのみ別構成**（ランディングとして扱う）
- **本文の横幅は全画面で同じ**（`max-w-5xl`、ヘッダー・フッターと同値）。
  画面ごとに変えると、ヘッダーと本文の左端がずれ、画面を移った瞬間に
  幅が変わる。`src/screens/page-width.test.ts` が検査する
- モバイル用のスティッキーアクションバーは**モバイルのみ**に出す。PCには付けない

## 7. イベント詳細ページの構成

上から順に。`〜スペース〜` はセクション間の余白を示す。

```
イベント名                                      → 幹事には右端に［✎］（PCのみ）
ハッシュタグ
バナー（中止の告知、申込締切まで残り●日 など）

〜スペース〜

[カレンダー] 日時                    → 右揃えでカレンダー追加ボタン
[場所]       場所                    → 右揃えで Google Map リンク
[リンク]     場所（URLのとき）        → 文字そのものがリンク。地図ボタンは出さない
[お金]       参加費

〜スペース〜

［参加登録］［幹事メニュー］
参加条件を小さく表示
  （サーバー限定か、定員がある場合は残り●人、参加規約）

〜スペース〜

参加者一覧
  - 主催者もこの一覧に含める。主催者には王冠マークを付ける
  - 既定はアイコン＋名前のみ、最大6名程度
  - 「―― もっと見る ――」で展開し、コメント・オプションを含む全員を表示
  - **見出しが状態を言っている並びでは、行に状態の札を出さない。**
    「参加リクエスト（3）」の下に同じ札が3つ続くのは同じことを4回
    言っているだけで、名前を読む邪魔になる

〜スペース〜

イベント説明
［参加登録］［主催者へ連絡］［シェア］［共有］［通報］

〜スペース〜

主催者名＋アイコン（グループ主催の場合はグループを表示）
メタデータ（イベントID、作成日、最終更新日）
```

情報の並び（日時・場所・参加費・参加者）は `.rule-y` で囲う。
**間だけでなく上下の縁にも罫線を引く**（「罫線」の節を参照）。

### 説明の下の操作列

**参加操作（参加登録／参加登録済み／幹事メニュー）をいちばん左に再掲する。**
上にもあるが、説明を読み終えて「参加しよう」と決まるのはここ。読み切った
人を頭まで戻らせない。同じ操作の再掲なので「primary は1画面に原則1つ」には
抵触しない。

並びは近いものから外側へ:

```
自分の参加 → 主催者へ連絡 → シェア → 共有 → 通報
```

通報だけは向きが違う（相手を止める操作）ので右端に置く。

**大きさと文字の濃さは列の中で全部そろえる。** ここで差を付けると、
重要度の差ではなく作りの粗さとして読まれる。主従は参加操作の色
（primary / state）だけで十分に伝わる。ラベルに `text-sm` や
`text-muted-foreground` を足さない。

揃える先は `size="sm"`（h-9）。情報行の「カレンダーに追加」と同じ高さ。
本文の頭に単独で置く参加ボタンはこの列ではないので h-12 のまま。

**列は本文の幅いっぱいに使う。** 画面が広いときは2つの組を両端へ寄せ、
スマホでは**どのボタンも伸ばして幅を分け合う**（`grow`）。伸ばすのは
ボタン自身で、**間隔は広げない**（`justify-between` にしない）。アイコンだけの
ボタンは幅が変わらないので、間隔で散らすとボタンとボタンの間にだけ余白が
空いて、並びが途切れて見える。中に2つ持っている組（シェアと共有）には
`grow-[2]` を与える — 1つ分だと、そこだけ2つで1つ分の幅を分けることになる。

**どのボタンも横幅を伸ばさない**（`w-full` / `flex-1` を持たせない）。
1つでも伸びると、狭い画面でその行を独り占めして「1行1ボタン」に崩れる。

**スマホでは2つの組に分けて改行する。** 自然な折り返しには任せない。

```
1行目: 自分の参加 → 連絡                          （そのイベントに関わる行動）
2行目: シェア → 共有 → カレンダー → 地図 → 通報   （外へ出す・外のアプリへ渡す）
```

2行目のカレンダーと地図は**情報行に出ているものの再掲**。狭い画面では
情報行の右端が本文の向こう側に埋もれるので、操作を探す人が見る列にも置く。
画面が広いときは出さない（同じ行き先への入口を2つ並べない）。

**「連絡」は行き先が2つある。** 主催者へ（anypost.dev）と、参加者全員へ
（このサイトの連絡画面）。両方ある閲覧者にだけプルダウンにして、
片方しか無ければその行き先のボタンをそのまま出す。参加者全員への連絡は
幹事だけのものではない — 連絡画面のAPIが参加者を通すので、そこに合わせる。

折り返しに任せると、参加状態のラベルの長さ（「参加登録」と「満員のため
受付を終了しました」）で境目が動き、同じ画面がイベントごとに違う形に崩れる。
2行目の3つは `sm` 未満で文字を畳み、アイコンだけにする（情報行の
「カレンダーに追加」「地図」と同じ扱い）。畳む側には `aria-label` と
`title` を必ず持たせる。**「主催者へ連絡」は畳まない** — 封筒のアイコン
だけでは、連絡なのか通知の設定なのかが読めない。
シェアのロゴも狭い画面では4つに減らす（8つ並べるとボタンだけで画面幅の
6割を占める）。上部の参加ボタンは単独で置くので広く取ってよい —
**幅いっぱいにするのは、行に1つしか置かないときだけ。**

日程調整の詳細（`PreEventDetailView`）も**まったく同じ並び**にする。

**場所の欄はリアルの会場とオンラインの会場を兼ねる。**
`http://` `https://` で始まればオンライン、それ以外は住所
（判定は `components/event/location.ts`）。
オンラインの会場を別欄に分けると、
オンラインのイベントで「場所」が空のまま別の欄だけ埋まる形になる。
**同じ行き先への入口を2つ置かない** — 住所は本文＋右端の地図ボタン、
URLは文字そのものをリンクにして、地図ボタンは出さない。

### 操作の挙動

- **参加登録ボタン** → モーダルを開く
- **参加登録済みボタン** → 同じモーダルを変更として開く。
  **キャンセルは出欠回答の選択肢のひとつ**にしてある。別のモーダルに分けると、
  変更しに来た人が一度閉じて別のボタンを探すことになる
- **幹事メニューボタン** → その場でメニューを開く。イベントの編集 /
  参加者の編集 / 出欠登録 / 参加者のCSV出力 へのリンク。
  **自分自身の参加操作はここに入れない** — 参加するかどうかは一般の参加者と
  同じ判断なので、幹事にも参加者用のボタンを隣に並べる
- **編集ボタン（題名の右）** → 幹事だけに出す。編集画面へ直接移る。
  幹事メニューにも同じ行き先があるが、直しに来た人がまず探すのは題名のそば。
  **記号だけ・PCのみ。** 語を添えると題名の横幅を削るし、スマホで編集しに
  来ることはまず無い（狭い画面では幹事メニューから行く）

## 8. 一覧まわりの共通部品

- **ページ最上部に戻り先を置く。** `‹ イベントを探す` のような文字リンクにする。
  ボタンにすると、その画面の主役の操作に見える
- **狭い画面では選択肢のラベルを落とす。** 3つ以上並ぶと横がはみ出す。
  記号（○△×など）だけを残し、語は `sr-only` で読み上げへ回す
- **択一の選択は `SegmentedControl`。** 塗りは「今どれを選んでいるか」の印。
  **選択肢ごとに色を変えない**（ラジオボタンがどれを選んでも同じ色で塗られる
  のと同じ）。意味の違いはアイコンとラベルで示す。
  結果を左右する選択には `options[].tone: 'primary'` を付けて青く塗り、
  表示の絞り込みでは中立のままにする。選択中の区画が動いて追えるので、
  どこからどこへ切り替わったのかが分かる。溝は押し込み、つまみは押し出し
  （ToggleSwitch と同じ立体の使い分け）。選択肢は等幅
- **絞り込みとページはクエリ文字列に持つ。** 「終了したイベントの2ページ目」を
  そのまま貼れて、戻るで元の位置へ帰れる。既定値はURLに書かない
- **ページ送りは `Pagination`。** PC はページ番号、モバイルは前後と現在地だけ。
  狭い画面に番号を詰めると、指の幅より小さい的が並ぶ。
  1ページに収まるときは出さない
- **カードは全体が押せる。** ただしリンクは入れ子にしない（`<a>` の中に
  `<a>` は置けない）。カードは div にし、タイトルのリンクを疑似要素
  （`after:inset-0`）でカード全体に広げる。ハッシュタグのように別の
  行き先を持つ要素は `relative z-10` でその上に載せる
- **1ページの件数は6の倍数。** カードは 1 / 2 / 3 列に並ぶので、どの幅でも
  行が半端に余らない。モバイル6件・PC12件を既定にする
